# AGENTS.md — маршрутизатор контуров `kurs_na_sever`

Перед чтением, поиском или изменением файлов сначала выбери ровно один рабочий
контур. Не используй соседнее приложение как неявный источник кода, данных,
компонентов, навигации или доменной модели.

## Landing

Рабочие пути:

- `index.html`;
- `styles/`;
- `scripts/`;
- `assets/`;
- `docker/`, `Dockerfile`, `docker-compose.yml`;
- `docs/brand-spec.md`, `docs/content-map.md`.

Landing — самостоятельное статическое приложение. Не открывай и не изменяй CRM
или Tracker, если пользователь явно не поставил интеграционную задачу.

## CRM

Рабочие пути:

- `apps/crm-backend/`;
- `apps/crm-frontend/`;
- `docs/cabinet/`;
- `docs/migration/`.

Внутри `apps/crm-backend/` и `apps/crm-frontend/` обязательно действуют
вложенные `AGENTS.md`. Не
переноси в CRM визуальный язык Landing или продуктовые решения Tracker.

## Интеграционный шов Landing ↔ CRM

Пути `docs/api-contract.md`, `scripts/api-client.js` и `docker/nginx/` открываются
только для явно поставленной интеграционной задачи. Изменения должны оставаться
в пределах версионированного контракта и проверяться с обеих сторон.

## Tracker

Tracker не является runtime-приложением этого репозитория. Его рабочий Git root:

`/Volumes/KINGSTON/Coding/ks_projects_tracker`

При Tracker-задаче остановись, проверь `cwd` и `git rev-parse --show-toplevel`,
затем работай только в Tracker-репозитории. Не создавай здесь Tracker UI, Graph,
AI, registry, API, модели или runtime.

`docs/design/**` и `output/**` в этом репозитории — только исторические
reference/handoff-артефакты. Их можно читать только по точному пути в явно
поставленной reference-задаче; они не являются implementation source.

## Общие правила границ

- Cross-contour изменение требует явного пользовательского scope и локального
  versioned-контракта в целевом репозитории.
- Искать и индексировать только пути выбранного контура.
- Не использовать относительные filesystem-imports между репозиториями.
- Сохранять чужие dirty/untracked-файлы и индексировать только точные task paths.
- `git add -A` запрещён в смешанном рабочем дереве.

## Git: одна задача — одна ветка

- Перед созданием ветки сначала выполни `git branch -a` и `gh pr list`; если для
  той же цели уже есть активная ветка или PR, продолжай работу в ней.
- Не создавай отдельные ветки для агентов, чатов, этапов проверки, мелких
  исправлений или повторных запусков одной задачи. Все участники одной задачи
  работают в общей task-ветке и индексируют только свои точные пути.
- Новая ветка допустима только для новой независимой цели, которую нельзя
  безопасно выполнить в существующей task-ветке. Имя ветки описывает результат,
  а не исполнителя или номер попытки.
- Одновременно поддерживай минимальный набор веток: `main` и только реально
  активные task-ветки. Не используй ветку как способ спрятать dirty worktree.
- После merge проверь SHA в `origin/main`, удали merged-ветку на GitHub и локально,
  затем выполни `git fetch --prune`. Ветка без незавершённой задачи не сохраняется.
- Перед новым PR сначала проверь, нельзя ли обновить уже открытый PR с тем же
  бизнес-результатом. Дублирующие PR и параллельные ветки для одной цели запрещены.
