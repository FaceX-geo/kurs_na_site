## 1. Цель и границы

Цель миграции — перенести полезные данные из текущего Bitrix-контура в новую управляемую систему так, чтобы:

- пользователи продолжили работу без потери карточек, истории, документов и связей;
- каждая исходная запись получила объяснимый результат: перенесена, объединена, отклонена или осознанно исключена;
- конфликтные решения оставались под контролем ответственного человека;
- новая модель не наследовала технический хаос и скрытые связи старой базы;
- повторные прогоны были идемпотентными и давали сопоставимый результат;
- после переключения можно было доказать полноту и корректность переноса.

В договорный контур входят:

- сайт и формы первичного обращения;
- CRM с двумя воронками: переезд и студенческая практика;
- работодатели, контакты, рекомендации и направления;
- карточки, история, документы, коммуникации, задачи и отчёты;
- отдельный модуль проектного управления;
- импорт из Bitrix с сохранением истории и очередью конфликтов.

Важно: договор описывает CRM, сайт и проектный модуль, но не полноценную ERP. Финансовый учёт, закупки, склад, бюджетирование, начисления и бухгалтерские проводки нельзя считать согласованным объёмом миграции. Архитектура оставляет для них явные интеграционные границы, однако добавление ERP-контуров требует отдельной модели, правил и критериев приёмки.

## 3. Обязательные предпосылки

До первой загрузки должны быть выполнены следующие условия:

1. Дамп помещён в неизменяемое хранилище, проверен по SHA-256 и зарегистрирован как snapshot.
2. Получен отдельный архив файлов Bitrix, включая каталог загрузок и фактическое хранилище Bitrix Disk. SQL-дамп содержит метаданные, но сам по себе не доказывает наличие бинарных файлов.
3. Источник восстановлен в изолированную MySQL-среду без исходящего сетевого доступа.
4. Доступ к восстановленной базе выдан отдельной read-only роли.
5. Зафиксированы владелец миграции, владельцы доменов CRM, проектного модуля, сайта, документов и безопасности.
6. Согласованы часовой пояс представления дат, правила хранения UTC и формат локального времени.
7. Утверждены словари статусов двух воронок и таблица соответствия старых и новых стадий.
8. Утверждены обязательные поля каждой целевой сущности.
9. Принято решение по глубине переноса чатов, почтовых сообщений, календаря и бизнес-процессов: рабочие данные, архив или осознанное исключение.
10. Утверждены допустимое окно недоступности, RPO, RTO и момент окончательного запрета записи в старую систему.

Пока любой пункт отсутствует, миграция может выполняться только как пробный прогон, но не как production cutover.

## 4. Целевая архитектура

### 4.1. Принцип

Рекомендуемая стартовая архитектура — модульный монолит с явными bounded contexts, одной транзакционной платформой и раздельными схемами данных. Для текущего объёма это проще в эксплуатации и надёжнее распределённой микросервисной схемы, но сохраняет возможность выделить нагруженный модуль позже.

Логическая схема:

```text
Сайт / кабинет / внутренний интерфейс
                  |
          API и контроль доступа
                  |
        Модульный монолит приложения
  ┌──────────┬──────────┬──────────┬──────────┐
  │ Identity │   CRM    │ Projects │ Content  │
  ├──────────┼──────────┼──────────┼──────────┤
  │ Comms    │Documents │ Reporting│  Audit   │
  └──────────┴──────────┴──────────┴──────────┘
                  |
      PostgreSQL + Outbox + Object Storage
                  |
       фоновые workers и интеграции
```

Базовые компоненты:

- PostgreSQL — канонические транзакционные данные;
- S3-совместимое объектное хранилище — документы и версии файлов;
- transactional outbox — надёжная доставка уведомлений и интеграционных событий;
- очередь фоновых работ — импорт, антивирусная проверка, формирование PDF, почта и Max;
- Redis — только для кэша, ограничителей и короткоживущего состояния, не как источник истины;
- централизованные структурированные логи, метрики и трассировка;
- отдельный migration runner с версионируемыми правилами преобразования.

### 4.2. Bounded contexts

| Контекст | Ответственность | Что не должен владеть |
|---|---|---|
| Identity & Access | учётные записи, роли, группы, сессии, MFA, политики доступа | бизнес-статусы CRM |
| CRM Core | контакты, компании, участники, рекомендатели, сделки, связи | проектная иерархия и проектные задачи |
| Program Workflows | две воронки, стадии, переходы, документы, история статусов | произвольные workflow Bitrix |
| Employer Relations | работодатели, образовательные организации, направления, вакансии, связи с кандидатами | бухгалтерские операции |
| Project Management | направления, проекты, подпроекты, задачи, подзадачи, Kanban, Gantt | CRM-активности по сделкам |
| Content & Intake | страницы сайта, формы, истории, вакансии, муниципалитеты, согласия | ручная редактура CRM-истории |
| Communications | email, Max, шаблоны, исходящие сообщения, статусы доставки | канонические карточки CRM |
| Documents | метаданные, версии, права, антивирусная проверка, PDF | пароли и интеграционные токены |
| Reporting | витрины, согласованные показатели, экспорт | изменение транзакционных данных |
| Audit | неизменяемый журнал действий и административных решений | бизнес-логика доменных модулей |
| Migration | staging, provenance, ledger, rejects, reconciliation | постоянное обслуживание UI после завершения миграции |
| AI Assistant | безопасный доступ через доменные API и разрешённые документы | прямой неограниченный доступ к БД |

Каждый контекст получает собственную схему PostgreSQL и публичный прикладной интерфейс. Межмодульные записи напрямую не изменяются. Внутри одной транзакции допустим синхронный вызов модуля; внешние эффекты передаются через outbox.

### 4.3. Разделение задач CRM и проекта

Нельзя переносить все записи `b_tasks` в один универсальный тип задач без классификации.

- `crm_activity` — звонок, письмо, встреча, напоминание или follow-up, связанный с контактом, компанией либо сделкой.
- `project_task` — единица исполнения проекта с родителем, исполнителем, сроком, зависимостями, доской и Gantt.
- `notification_job` — техническая доставка уведомления; это не пользовательская задача.

Общие поля и UI-компоненты могут переиспользоваться, но статусы, права, связи и жизненный цикл должны быть типизированы отдельно. Неоднозначные 89 legacy-задач направляются в очередь ручной классификации, а не автоматически превращаются в проектные задачи.

## 5. Каноническая модель

Все канонические записи получают UUIDv7. Legacy-ID хранится не как основной ключ, а в `legacy_reference` с уникальностью по паре `(source_system, source_entity, source_id)`.

### 5.2. Общие обязательные поля

Для мигрируемых сущностей:

- `id`;
- `created_at`, `updated_at`;
- `created_by`, `updated_by`, если автор известен;
- `record_status`;
- `data_classification`;
- `source_system`;
- `migration_run_id`;
- payload integrity checksum для non-PII либо semantic `HMAC-SHA-256`
  fingerprint с `purpose` + `key_version`; raw/unkeyed PII hash запрещён;
- `row_version` для оптимистической блокировки.

Дата в базе хранится в UTC. Исходный timezone и исходная строка сохраняются в provenance, если преобразование неоднозначно.

## 7. Migration Control Plane

Миграция выполняется через отдельный технический контур. Прямые `INSERT` из legacy в канонические таблицы запрещены.

### 7.1. Управляющие таблицы

`migration_run`

- идентификатор и версия кода миграции;
- checksum источника;
- режим `dry_run`, `rehearsal`, `cutover`;
- время начала/окончания;
- статус;
- инициатор и подтверждающие лица.

`source_snapshot`

- система и снимок;
- checksum дампа;
- параметры MySQL;
- ссылка на файловый snapshot;
- граница извлечения и timezone.

`stg_record`

- `run_id`;
- `source_table`, `source_pk`;
- предполагаемый `entity_type`;
- исходный payload в JSONB;
- нормализованный payload;
- source hash;
- статус валидации.

`stg_relation`

- исходная и целевая сторона legacy-связи;
- тип связи;
- результат разрешения;
- причина неразрешённой связи.

`normalization_issue`

- поле, исходное значение, код проблемы;
- автоматическое действие;
- уровень риска.

`identity_candidate`

- набор записей-кандидатов на объединение;
- сравниваемые ключи;
- score и объяснение;
- предложенный survivor.

`conflict_case`

- конфликтующие значения;
- влияние на бизнес;
- рекомендованное решение;
- владелец решения;
- решение и его автор.

`reject_record`

- исходная ссылка;
- этап;
- стабильный код причины;
- безопасное описание;
- повторяемость;
- статус разбора.

`migration_ledger`

- исходная запись;
- действие `created`, `updated`, `merged`, `rejected`, `excluded`;
- target-ID;
- причина;
- source/target fingerprint;
- номер попытки.

`field_provenance`

- target entity и поле;
- source table/record/field;
- исходное значение либо его защищённый hash;
- применённое правило;
- время преобразования.

`reconciliation_result`

- метрика;
- область;
- ожидаемое и фактическое значение;
- порог;
- результат;
- ссылка на доказательство.

`file_manifest` и `file_transfer_attempt`

- legacy file ID, путь и версия;
- размер, MIME, checksum;
- владелец и права;
- target object key;
- статус проверки и доставки.

### 7.2. Идемпотентность

- каждая legacy-запись адресуется стабильной парой `(source_system, source_entity, source_id)`;
- повторный запуск делает upsert только при изменении `source_fingerprint`;
- правила трансформации версионируются;
- outbox-события имеют idempotency key;
- повторная отправка файла сверяет checksum и не создаёт дубликат версии;
- ручные решения конфликтов сохраняются отдельно и переиспользуются при новом прогоне.

## 8. Нормализация, дедупликация и survivorship

### 8.1. Нормализация

До поиска дублей:

- удалить только незначимые внешние пробелы, сохранив исходное значение;
- привести email к lowercase и проверить синтаксис;
- привести телефон к E.164 при известном регионе, отдельно сохранить extension;
- нормализовать ИНН и КПП как строки с проверкой длины и контрольных разрядов;
- нормализовать Unicode и похожие символы без необратимой подмены исходного текста;
- преобразовать даты в UTC с сохранением source timezone;
- разобрать PHP-сериализацию безопасным парсером без исполнения объектов;
- очистить HTML по allowlist, сохранив оригинал в защищённом staging;
- классифицировать пустое значение отдельно от нуля и `false`;
- перевести справочники по устойчивым кодам, а неизвестные значения направить в конфликт.

### 8.2. Правила дублей

Автоматически объединяются только детерминированные совпадения.

Контакт:

1. точное совпадение подтверждённого нормализованного телефона;
2. точное совпадение подтверждённого email;
3. совместное совпадение ФИО, даты рождения и дополнительного устойчивого признака.

Совпадение только по ФИО не является основанием для auto-merge.

Организация:

1. точное совпадение валидного ИНН, при необходимости с КПП;
2. официальный legacy-link на одну организацию;
3. без ИНН — совпадение названия, домена и адреса создаёт кандидата, но требует решения человека.

Сделка:

- уникальна по legacy-ID в рамках источника;
- не объединяется только из-за одинакового человека и стадии;
- предполагаемые повторные сделки рассматриваются как отдельный conflict case.

Направление работодателю:

- сохраняет собственный legacy-ID;
- возможный дубль определяется по кандидату, работодателю, вакансии/направлению и временному окну;
- автоматическое объединение разрешается только по утверждённому бизнес-правилу.

### 8.3. Survivorship

При подтверждённом merge:

1. подтверждённое значение важнее неподтверждённого;
2. значение из профильной канонической сущности важнее копии из события или timeline;
3. заполненное значение не заменяется пустым;
4. более новое значение выигрывает только при надёжном `updated_at`;
5. ручное подтверждение владельца домена имеет высший приоритет;
6. все проигравшие значения остаются в provenance и доступны аудитору;
7. связи, документы и история всех дублей перепривязываются к survivor без потери исходных ссылок.

Fuzzy matching используется для формирования очереди, но не для необратимого автоматического слияния.

## 10. Сверка и доказательство полноты

### 10.1. Баланс исходных записей

Для каждой таблицы и доменной сущности:

```text
extracted =
  created
  + updated
  + merged
  + rejected
  + intentionally_excluded
```

Каждая исходная запись должна иметь ровно один финальный исход в ledger. Ledger coverage:

```text
ledger_coverage = classified_source_records / extracted_records × 100%
```

Требование для cutover: `ledger_coverage = 100%`.

### 10.2. Целевые метрики

| Метрика | Формула | Порог go-live |
|---|---|---:|
| Покрытие ledger | классифицированные / извлечённые | 100% |
| Полнота критичных сущностей | мигрированные пригодные / пригодные в источнике | 100% |
| Неразобранные blocking rejects | количество | 0 |
| Неразобранные blocking conflicts | количество | 0 |
| Сироты в критичных связях | неразрешённые обязательные связи | 0 |
| Валидность обязательных полей | валидные / проверенные | 100% |
| Паритет критичных полей в выборке | совпавшие / проверенные | 100% |
| Паритет некритичных полей в выборке | совпавшие / проверенные | не ниже 99,5% |
| Критичные файлы | совпавшие checksum / ожидаемые | 100% |
| Все файлы/ACL/storage для `FULL_MIGRATION_READY` | binary + binding + checksum + ACL + malware на одном watermark | 100%; любой подписанный остаток означает только `PARTIAL_MIGRATION_ACCEPTED` |
| Повторный прогон | неожиданные новые дубли/изменения | 0 |

«Пригодная запись» определяется утверждёнными правилами, а не удобством мигратора. Исключение должно иметь код причины, владельца и доказательство.

### 10.3. Проверки связей

Обязательны:

- дело → человек;
- дело → воронка и стадия;
- направление → кандидат и работодатель;
- рекомендация → рекомендатель и кандидат;
- документ → владелец;
- activity/timeline → существующий объект;
- project task → проект;
- подзадача → существующий родитель;
- authored event → пользователь либо явный `legacy_system_actor`.

В источнике нет объявленных FK, поэтому связи проверяются программно по фактическим ID и бизнес-семантике. В целевой модели обязательные связи должны быть защищены FK и доменными ограничениями.

### 10.4. Контрольные выборки

Минимальная выборка включает:

- по 20 карточек с каждой стадии обеих воронок;
- все записи с пустыми обязательными полями;
- все merge-группы более чем из двух записей;
- все 7 лидов;
- не менее 30 направлений работодателям;
- не менее 30 карточек с документами;
- самые старые и самые новые записи;
- записи с кириллицей, HTML, PHP-сериализацией и несколькими телефонами/email;
- карточки удалённых и деактивированных пользователей;
- задачи с родителем, несколькими участниками и просрочкой.

Проверка выполняется одновременно:

- автоматически по ID, hash, counts и связям;
- визуально в новом интерфейсе владельцем домена;
- выборочно по оригинальной карточке Bitrix.

### 10.5. Business reconciliation

Перед cutover владельцы подтверждают:

- количество активных дел по каждой воронке и стадии;
- количество участников по типам;
- количество работодателей и образовательных организаций;
- количество направлений по статусам;
- количество незавершённых активностей по ответственным;
- количество документов по категориям;
- согласованные отчётные показатели на контрольную дату.

Если формула показателя в старом отчёте не доказана, он не считается эталоном автоматически: формула документируется и утверждается отдельно.

## 11. Миграция файлов

SQL-дамп нельзя считать полным источником документов. Для `b_file`, `b_disk_object` и `b_disk_version` нужен физический файловый snapshot.

Порядок:

1. Получить read-only DB и `/upload` snapshots с отдельными signed IDs на одном
   freeze watermark.
2. Построить manifest: legacy-ID, версия, путь, имя, размер, MIME, дата,
   storage, owner, source ACL principal/effect и binding.
3. Рассчитать SHA-256 каждого бинарного объекта.
4. Сопоставить metadata-only записи и отсутствующие файлы.
5. Отсутствующие файлы направить в reject с кодом `FILE_BINARY_MISSING`.
6. Проверить расширение против MIME и провести антивирусную проверку.
7. Опасные объекты изолировать в quarantine.
8. Загрузить файлы под непрогнозируемым object key с default-deny ACL.
9. Создать document/version только после подтверждённой загрузки.
10. Повторно скачать выборку и проверить checksum end-to-end.
11. Reconcile 100% ACL/storage rows, versioned `TASK_ID` permission crosswalk,
    unknown principals/orphans и malware results; любой ненулевой остаток
    блокирует FULL.
12. Для двух legacy external links выполнить signed revoke/reissue/exclude;
    старые `HASH/PASSWORD/SALT` не импортировать.

Ссылки в HTML и timeline переписываются через таблицу legacy URL → document ID. Временные signed URL не сохраняются как постоянные значения.

Terminal file status обязан быть ровно одним:
`FULL_MIGRATION_READY` только при 100% reconciliation либо
`PARTIAL_MIGRATION_ACCEPTED` при любом подписанном binary/ACL exception.
Scope-change escape для заявления FULL отсутствует.

Не переносятся:

- включить MFA и минимально необходимые роли;
- вести отдельный журнал ротации без значений секретов.

Персональные данные:

- production-дамп не используется в локальной разработке;
- для dev/test формируется маскированный dataset;
- телефон, email, адреса и документы редактируются в логах;
- исходный staging шифруется и доступен только миграционной роли;
- экспорт конфликтов не должен содержать лишние поля;
- каждый просмотр или изменение конфликтной карточки аудируется;
- срок хранения staging и дампов утверждается заранее;
- удаление выполняется только после formal sign-off и окончания rollback-периода.

AI Assistant получает данные только через доменные API с проверкой RBAC, ограничением области и журналом запросов. Прямой SQL-доступ модели к production запрещён.

### 12.1. Безопасная архитектура AI Assistant

На первом этапе ассистент поддерживает только два явно разделённых режима:

1. **Отчёт на чтение** — отвечает по разрешённым данным через типизированные report tools.
2. **Черновик действия** — готовит изменение, но не исполняет его без проверки и подтверждения пользователя.

Поток изменения:

```text
намерение пользователя
→ структурированный типизированный draft
→ валидация полей и бизнес-правил
→ проверка RBAC и области доступа
→ понятный preview/diff
→ явное подтверждение человека
→ идемпотентная доменная команда
→ transactional outbox
→ audit event и результат пользователю
```

Примеры допустимых draft-действий:

- создать CRM-активность по конкретному делу;
- подготовить типизированную project task в выбранном проекте;
- предложить изменение стадии с объяснением требуемых полей;
- подготовить письмо или сообщение Max без автоматической отправки;
- собрать фильтрованный отчёт для экспорта.

CRM-активность и project task имеют разные схемы draft, валидаторы, права и команды. Ассистент не должен создавать «универсальную задачу», смысл которой определяется свободным текстом.

Ограничения:

- нет прямого доступа к PostgreSQL, shell, object storage и произвольным внутренним инструментам;
- нет автономной записи, смены стадии, массовой рассылки или назначения прав;
- модель вызывает только allowlisted доменные команды с JSON Schema;
- сервер повторно проверяет RBAC, tenant/scope и бизнес-инварианты, даже если draft уже прошёл проверку;
- подтверждение привязано к hash предпросмотра и истекает при изменении данных;
- команда имеет idempotency key, безопасно повторяется и публикует внешние эффекты через outbox;
- retry не должен создавать дубли задач, сообщений или стадий;
- каждое предложение, подтверждение, исполнение и отказ записываются в audit.

Отчётный ответ обязан показывать:

- период и timezone;
- применённые фильтры;
- доступную пользователю область данных;
- время актуальности источника;
- формулу показателя;
- ссылки/provenance до карточек или агрегатов, из которых получен вывод;
- предупреждение о неполных или отфильтрованных данных.

Персональные данные передаются модели по принципу минимальной необходимости. Поля маскируются до вызова модели, если полное значение не нужно для сценария; секреты не передаются никогда. Ответ повторно проходит redaction и policy-check перед показом пользователю.

Для понятного новичку интерфейса:

- ассистент формулирует, что он понял и что именно предлагает;
- preview показывает объект, изменяемые поля, старое и новое значение;
- критические последствия объясняются обычным языком;
- основные действия называются «Подготовить», «Проверить» и «Подтвердить», а не техническими командами;
- пользователь может отредактировать draft или отменить действие без побочных эффектов;
- при ошибке показывается причина и безопасный следующий шаг;
- для массового действия отображаются объём, выборка и несколько примеров до подтверждения.

Надёжность AI-контура проверяется отдельным evaluation-набором:

- корректность выбора report tool или draft action;
- отсутствие выхода за RBAC/scope;
- точность фильтров, дат и агрегатов;
- наличие provenance в отчёте;
- отсутствие скрытой записи без подтверждения;
- идемпотентность повторной команды;
- устойчивость к prompt injection в карточках и документах;
- корректный отказ при недостатке данных;
- PII/redaction;
- fallback без модели.

Fallback обязателен: если модель, провайдер или evaluation-guard недоступны, пользователь продолжает работать через обычные фильтры, формы, отчёты и типизированные команды. AI ускоряет работу, но не является единственной точкой доступа к бизнес-функции.

## 13. Cutover

### T−14 дней

- завершить mapping и правила дедупликации;
- провести полную репетицию;
- измерить время extract/transform/load/reconcile;
- проверить процедуру rollback;
- обучить владельцев конфликтной очереди.

### T−7 дней

- заморозить изменения схем и справочников;
- закрыть blocking rejects;
- проверить файловый snapshot;
- утвердить коммуникацию пользователям;
- назначить decision owner go/no-go.

### T−48 часов

- подтвердить актуальный backup и восстановление;
- выполнить rehearsal на максимально свежих данных;
- проверить мониторинг и доступы;
- сверить контрольные отчёты;
- запретить несогласованные релизы обеих систем.

### T−24 часа

- зафиксировать границу initial snapshot;
- начать предварительную загрузку неизменяемых объектов и файлов;
- проверить запас места и производительность;
- подготовить страницу статуса и канал инцидента.

### T0

1. Включить write freeze для Bitrix.
2. Остановить приём форм или временно поставить их в надёжную очередь.
3. Зафиксировать финальную временную границу.
4. Извлечь delta.
5. Выполнить идемпотентный delta import.
6. Запустить полную reconciliation.
7. Выполнить smoke-тесты ролей, воронок, карточек, истории, файлов, форм и отчётов.
8. Получить подписи технического владельца, владельцев CRM/проекта и безопасности.
9. Переключить сайт, формы и пользовательский вход.
10. Оставить Bitrix в read-only режиме.
11. Включить усиленный мониторинг и поддержку.

Не допускается длительный неуправляемый dual-write. Если короткий dual-write неизбежен, он проектируется отдельно с владельцем конфликтов и двусторонним ledger.

## 14. Rollback

Rollback должен быть проверен на репетиции, а не существовать только как текст.

Триггеры:

- утрата или недоступность критичных карточек;
- невозможность войти у значимой группы пользователей;
- неправильные права или утечка данных;
- нарушение связи дело–участник–работодатель;
- недоступность критичных документов;
- расхождение контрольных показателей выше согласованного порога;
- необратимая ошибка интеграций или форм;
- превышение утверждённого окна cutover.

Порядок:

1. Decision owner объявляет rollback.
2. Новая система переводится в maintenance/read-only.
3. Входящие формы направляются в защищённую очередь.
4. Фиксируется target delta после T0.
5. Трафик и формы возвращаются на Bitrix.
6. При необходимости снимается write freeze старой системы.
7. Пользователи получают единое сообщение о состоянии.
8. Инцидент и все действия записываются в audit.
9. Target delta сохраняется для разбора и последующего replay; данные не удаляются.

После успешного переключения Bitrix остаётся read-only на согласованный rollback-период. Архив нельзя уничтожать до business sign-off, проверки восстановления и окончания юридического срока хранения.

## 15. Human-in-the-loop gates

| Gate | Автоматизируется | Решает человек |
|---|---|---|
| Scope gate | инвентаризация и классификация | что мигрируется, архивируется и исключается |
| Mapping gate | статистика полей и предложенная карта | бизнес-смысл пользовательских полей |
| Dedupe gate | deterministic/fuzzy candidates и score | неоднозначные объединения |
| Data quality gate | rejects, orphan checks, обязательные поля | допустимость исправления или исключения |
| Access gate | сравнение ролей и effective permissions | выдача чувствительных полномочий |
| File gate | manifest, checksum, malware scan | судьба отсутствующего/опасного файла |
| Reconciliation gate | counts, hashes, samples | приемлемость бизнес-показателей |
| Go/no-go | автоматический dashboard readiness | окончательное переключение |
| Rollback | мониторинг и триггеры | решение о возврате |
| Archive deletion | подтверждение сроков и backup | разрешение на уничтожение |

Все решения человека должны иметь автора, время, основание и область действия. Решение, принятое для одного конфликта, нельзя молча распространить на весь набор данных.

## 16. Go/no-go checklist

### Данные

- [ ] checksum исходного SQL совпадает;
- [ ] файловый snapshot получен и имеет manifest;
- [ ] ledger coverage равен 100%;
- [ ] нет blocking rejects;
- [ ] нет blocking conflicts;
- [ ] нет сирот в критичных связях;
- [ ] все обязательные поля валидны;
- [ ] критичные файлы подтверждены на 100%;
- [ ] ACL/storage/principals/TASK_ID crosswalk reconciled; unknown/orphan = 0;
- [ ] external-link decisions подписаны, legacy secrets не импортированы;
- [ ] terminal status явно выбран:
      `FULL_MIGRATION_READY` или `PARTIAL_MIGRATION_ACCEPTED`; PARTIAL не
      называется полной миграцией;
- [ ] контрольные выборки подписаны владельцами;
- [ ] показатели двух воронок сверены.

### Приложение

- [ ] роли и права проверены отдельными тестовыми пользователями;
- [ ] обе воронки и переходы стадий работают;
- [ ] карточка участника, работодателя и дела открывается;
- [ ] история не содержит очевидных дублей;
- [ ] CRM-активности не смешаны с project tasks;
- [ ] документы открываются только авторизованным ролям;
- [ ] формы создают заявку идемпотентно;
- [ ] email/Max используют новые credentials и outbox;
- [ ] отчёты используют согласованные формулы;
- [ ] audit фиксирует критичные действия.

### Эксплуатация

- [ ] backup целевой системы создан и проверено восстановление;
- [ ] rollback rehearsal успешно завершён;
- [ ] RPO/RTO и окно переключения утверждены;
- [ ] dashboard миграции и алерты доступны;
- [ ] назначены incident commander и decision owner;
- [ ] служба поддержки и пользователи уведомлены;
- [ ] legacy Bitrix готов к read-only режиму;
- [ ] план ротации/отзыва секретов готов;
- [ ] запрещены несогласованные релизы на время cutover.

Go разрешён только при подтверждении всех обязательных пунктов. Пропуск пункта фиксируется как формально принятый риск с владельцем и сроком, но критичные безопасность, целостность, backup и rollback пропускать нельзя.

## 17. Наблюдаемость

Для каждого run публикуются:

- состояние и длительность этапов;
- rows/sec и bytes/sec;
- количество `created`, `updated`, `merged`, `rejected`, `excluded`;
- распределение кодов ошибок;
- размер conflict queue и её возраст;
- неразрешённые связи;
- прогресс файлов по количеству и байтам;
- расхождения reconciliation;
- количество повторных попыток;
- ошибки outbox и интеграций.

Логи структурированы по `run_id`, `source_reference`, `target_id`, `step`, `attempt`, но не содержат токены, полные документы, email и телефоны. Для пользовательского dashboard показываются причина, владелец и следующий шаг, а не только технический stack trace.

## 18. Автоматизировать сразу

- генерацию schema/data inventory из read-only источника;
- проверку SHA-256 и регистрацию snapshot;
- профилирование обязательности и уникальности полей;
- deterministic normalization;
- формирование dedupe candidates;
- ledger и provenance;
- orphan checks;
- count/hash reconciliation;
- file manifest, checksum и антивирусную проверку;
- dry-run и повторный идемпотентный прогон;
- dashboard readiness;
- выгрузку conflict queue без лишних персональных данных;
- smoke-тесты критичных пользовательских сценариев;
- формирование подписываемого отчёта cutover.

Под контролем человека остаются бизнес-смысл полей, неоднозначный merge, права, исключения, трактовка показателей, go/no-go, rollback и удаление архивов.

## 19. Немедленные следующие шаги

1. Получить физический snapshot файлов Bitrix и проверить его связь с 3 941 записями `b_file`, 961 объектом и 671 версией Disk.
2. Восстановить SQL в изолированный MySQL 8 и выполнить referential/orphan profiling по фактическим данным.
3. Сформировать полный каталог 1 669 таблиц с решениями `migrate/archive/regenerate/exclude`.
4. Расшифровать все пользовательские поля CRM и смарт-процесса 1042 вместе с владельцем продукта.
5. Зафиксировать целевые стадии двух воронок и таблицу соответствия.
6. Утвердить, что считать CRM activity, а что project task.
7. Согласовать перенос либо архивирование `b_im_message`, почты, календаря и business-process history.
8. Согласовать deterministic dedupe и survivorship на реальных выборках.
9. Создать migration control schema и первый dry-run без записи в production.
10. Зафиксировать RPO, RTO, окно cutover, rollback-период и владельцев подписей.

Первый практический milestone — повторяемый dry-run, после которого для каждой пригодной записи контакта, компании, дела и направления существует ledger outcome, а все неоднозначности собраны в управляемую human-in-the-loop очередь.
