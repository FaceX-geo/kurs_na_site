# Аудит текущего состояния внутреннего кабинета

Статус: зафиксированный baseline после полного read-only миграционного аудита
Дата: 29.07.2026
Режим проверки: read-only

## 1. Цель аудита

Определить фактическую отправную точку для внутреннего CRM/трекера, не смешивая:

- готовый публичный сайт;
- существующие дизайн-референсы;
- документацию;
- реально работающий кабинет;
- исходные данные Bitrix;
- завершённую миграцию.

Бизнес-результат этапа — исключить ложное ощущение готовности, сохранить реальные связи сотрудников с кандидатами и построить кабинет как отдельную, управляемую систему.

## 2. Проверенные источники

- корень этого Git-репозитория;
- активная ветка и рабочее дерево Git;
- `Dockerfile`, `docker-compose.yml`, nginx-конфигурация и API-клиент;
- Bravo runtime через `scripts/bravo-compose.sh`;
- локальный gitignored-дамп `sitemanager-final.sql.gz`;
- документы `docs/migration/*`;
- 24 PNG-референса и их handoff/QA;
- подписанный договор и приложение ТЗ, страницы 7–13.

В аудит не входили изменения production-данных, создание пользователей, отправка сообщений, импорт в target-БД и cutover.

## 3. Фактическое состояние репозитория

### 3.1. Что работает сейчас

- публичный одностраничный сайт на HTML/CSS/vanilla JavaScript;
- один nginx-контейнер `kurs_na_site`;
- healthcheck статической страницы;
- локально подготовленные документы анализа, схемы и 24 визуальных референса;
- защищённый wrapper для удалённого Docker runtime на Bravo.

### 3.2. Чего в коде нет

| Контур | Фактическое состояние |
|---|---|
| CRM | нет backend, schema, API и UI приложения |
| Проектный трекер | нет доменной модели, API и UI |
| Вход и сессии | нет |
| RBAC | нет |
| Суперадмин | нет |
| Управление пользователями | нет |
| Смена/сброс пароля | нет |
| Журнал действий | нет хранилища и runtime |
| ИИ-помощник | есть спецификация и изображения, runtime отсутствует |
| Миграция | есть анализ и runbook, ETL и target отсутствуют |
| Автоматические тесты | нет |

В репозитории нет `package.json`, server-кода, ORM/SQL-миграций приложения и тестового каркаса.

### 3.3. Runtime-проверка

Bravo возвращает один и тот же публичный `index.html` для:

- `/`;
- `/cabinet`;
- `/crm`;
- `/projects`;
- `/admin`;
- `/login`;
- `/api/v1/dictionaries/spheres`.

Ответ `200 text/html` на внутреннем или API-маршруте не доказывает существование кабинета. Причина — nginx `try_files ... /index.html`. Для нового контура API-маршруты обязаны завершаться JSON-ответом/ошибкой и никогда не попадать в HTML fallback.

### 4.1. Критическое уточнение про сотрудников

Запись `b_user` не равна сотруднику и не равна будущей учётной записи.

Проверенная классификация по фактическим признакам:

- 191 пользователь связан с imconnector;
- 6 пользователей являются bot-аккаунтами;
- 1 — saleanonymous;
- 20 пользователей связаны с оргструктурой;
- из них 14 активны и 6 неактивны;
- 18 также входят в группу «Сотрудники».

До финальной сверки каждый из 218 source users обязан получить один явный migration outcome:

`active_employee`, `inactive_employee`, `service`, `external`, `duplicate`, `manual_review` или `excluded`.

Автоматически выдавать доступ всем 218 записям запрещено.

### 4.2. Подтверждённые связи

- у всех 3 186 контактов есть валидный source owner-user;
- 2 728 контактов назначены активным сотрудникам, 458 — неактивным;
- у всех 1 899 сделок есть валидный source owner-user;
- 1 829 сделок назначены активным сотрудникам, 70 — неактивным;
- 709 компаний назначены активным сотрудникам, 88 — неактивным;
- 1 808 направлений назначены активным сотрудникам;
- 88 задач назначены активным сотрудникам, 1 — неактивному;
- 1 514 сделок имеют основной контакт, 385 — без основного контакта;
- для 2 из 385 связь с кандидатом восстанавливается по структурному event relation;
- 383 сделки требуют решения владельца данных;
- со сделками связано 1 573 уникальных контакта;
- 1 613 контактов не имеют сделки;
- orphan между сделкой и контактом в проверенной связи: 0;
- 1 801 из 1 808 направлений работодателям связаны через entity relation со сделкой;
- 1 795 направлений полностью связаны с кандидатом и работодателем;
- 13 направлений неполны и требуют ручной очереди.

Эти числа не являются разрешением на механическое слияние. В target должны сохраняться разные семантики:

- владелец контакта;
- ответственный по делу/сделке;
- ответственный по направлению работодателю;
- автор/редактор активности;
- ответственный/создатель/исполнитель задачи;
- исторический актор таймлайна.

У 648 из 1 514 сделок с контактом owner сделки отличается от owner контакта. Только у 987 из 1 801 связанных направлений совпадают owner контакта, дела и направления. Поэтому «ответственный сотрудник» не может быть одним общим полем на все сущности.

### 4.3. Секреты и файлы

- legacy password hashes, токены, cookies и интеграционные секреты мигрировать запрещено;
- существующий пароль нельзя показать суперадмину;
- target-учётные записи получают новый reset/invite lifecycle;
- SQL-дамп не содержит бинарные файлы;
- полная файловая миграция невозможна без согласованного snapshot каталога `/upload`;
- текущий дамп должен быть добавлен в локальные защитные исключения Git и никогда не попадать в commit/image.

## 5. Договорный объём кабинета

Внутренний контур договора включает:

- две CRM-воронки «Переезд» и «Студенты»;
- карточку кандидата/сделки 360°, таймлайн и договорные вкладки;
- рекомендателей «Арктического маяка»;
- работодателей и направления;
- данные трудоустройства и переезда;
- CRM-задачи, email и Max;
- дашборды, уведомления и отчёты;
- импорт Bitrix с дедупликацией, историей, валидацией и ручной конфликтной очередью;
- самостоятельный проектный модуль;
- независимые роли CRM и проектного модуля;
- текстовый ИИ в обоих контурах.

Пользователь отдельно расширил объём:

- отчёты через ИИ;
- создание одной или нескольких задач обычной фразой;
- предельно понятный интерфейс для новичка;
- платформенный суперадмин;
- реестр и карточка пользователей;
- назначение ролей;
- смена/сброс паролей и отзыв сессий;
- полный журнал действий;
- перенос сотрудников и их связей с кандидатами/приезжающими;
- новый текстовый логотип «Курс на Север» со знаком «Роза Севера».

Публичный сайт в текущую реализацию кабинета не входит.

## 6. Состояние визуальных материалов

Существуют 24 выбранных референса:

- 1 foundation/shell;
- 10 CRM;
- 5 tracker;
- 4 AI;
- 3 migration;
- 1 responsive.

Они задают:

- визуальный shell;
- типографику и цветовые токены;
- плотность таблиц и карточек;
- CRM, tracker, AI и migration-паттерны;
- responsive-правила.

Они не доказывают:

- функциональность контролов;
- корректность данных;
- наличие auth/RBAC;
- работу API;
- сохранение изменений;
- защиту прямых URL;
- идемпотентность;
- миграцию;
- production readiness.

Отдельно не покрыты полноценными референсами:

- вход, MFA и восстановление доступа;
- реестр и карточка пользователя;
- preview эффективных прав;
- сброс пароля и управление сессиями;
- общий audit log и detail события;
- reconciliation сотрудников и их связей.

## 7. Критические риски

| ID | Риск | Последствие | Обязательный контроль |
|---|---|---|---|
| A-01 | Попытка встроить кабинет в публичный `index.html` | смешение контуров, риск PII и технический долг | отдельные web/API приложения и маршруты |
| A-02 | Все 218 `b_user` считаются сотрудниками | доступ получают боты/коннекторы/уволенные | классификация и кадровое подтверждение |
| A-03 | `user_account` смешан с `crm.person` | ошибочное объединение сотрудника и кандидата | разные сущности и ручная identity link |
| A-04 | Legacy password hashes/токены импортируются | компрометация target | denylist полей и secret scan |
| A-05 | Права проверяются только в UI | обход через API | deny-by-default на сервере и негативные E2E |
| A-06 | CRM task смешана с project task | нарушение независимости доменов | отдельные таблицы, API и permissions |
| A-07 | AI выполняет запись сразу | массовые ошибки и потеря контроля | draft → validate → preview → confirm → audit |
| A-08 | HTML fallback маскирует API error | ложный health и потеря заявок | отдельный API location и JSON errors |
| A-09 | Нет `/upload` | неполная история/вложения | файловый snapshot или явный reject ledger |
| A-10 | Cutover по старому dump | потеря delta | свежий snapshot, freeze/delta и reconciliation |
| A-11 | Аудит редактируем | скрытие изменений прав/данных | append-only store, отдельные права/retention |
| A-12 | Изображение принято как QA | нефункциональный прототип | E2E + data reconciliation + visual diff |

## 8. Архитектурное заключение

Кабинет должен быть новым additive-контуром рядом с публичным сайтом:

- отдельный `cabinet-web`;
- отдельный `core-api`;
- отдельная target-БД;
- отдельные namespaces/permissions для CRM и tracker;
- модуль identity/RBAC/session;
- append-only audit;
- migration staging/ledger;
- AI command gateway с обязательным подтверждением действий;
- worker/outbox для email, Max, импортов и повторов;
- object storage для новых вложений.

Сайт взаимодействует с кабинетом только через публичный intake API. Изменять интерфейс сайта для реализации внутренних сценариев не требуется.

## 9. Итог аудита

Документационная и визуальная база подготовлена хорошо, но рабочего внутреннего кабинета пока нет. Реализацию нельзя начинать с вёрстки отдельных картинок: сначала нужно зафиксировать доменную модель, роли, password lifecycle, аудит, state machines, migration ledger и доказательства приёмки.

Решение audit-gate:

- текущий сайт не является кабинетом;
- существующие PNG не являются рабочим прототипом;
- дамп проанализирован, но не мигрирован;
- миграция должна быть identity-aware и relation-aware;
- кабинет строится отдельно;
- следующий разрешённый этап — продуктово-техническое ТЗ и его red-team проверка.
